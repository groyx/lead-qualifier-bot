# lead-qualifier-bot

Telegram-бот квалификации входящих лидов для отдела продаж: проводит человека
по короткой анкете, считает скоринг и заводит сделку в CRM с расшифровкой,
почему лид горячий.

Сделан под задачу застройщика: тип объекта, бюджет, срок покупки, способ оплаты,
контакт. Сценарий описан данными, поэтому под другую нишу правится один список,
без изменения логики.

## Что внутри

**Всё тестируется без сети.** Telegram и CRM спрятаны за `Protocol`, реальные
адаптеры принимают HTTP-вызов аргументом. Диалог, скоринг, ретраи, дедупликация
и переживание перезапуска проверяются на мок-сервисах: ни токена, ни Битрикса,
ни интернета не нужно.

**Лид не теряется при перезапуске.** Сессии сохраняются на диск атомарно
(временный файл, fsync, `os.replace`). Человек ответил на четыре вопроса из
пяти, процесс перезапустился, диалог продолжается с того же места. Битый файл
состояния не мешает боту стартовать.

**Дубли в CRM не заводятся.** Ключ дедупликации по паре чат и телефон. Это не
теория: пользователь дважды жмёт кнопку, или ответ CRM теряется по таймауту
уже после создания сделки. Менеджер получает одну карточку, а не две.

**Временный отказ и отказ по данным разделены.** Недоступность CRM повторяется
с растущей паузой и джиттером. Отклонённый по валидации лид не повторяется
вообще: данные от этого не починятся, а попытки сгорят.

**Пользователь не видит аварий.** Если CRM не ответила после всех попыток,
человеку показывается спокойный текст, ответы остаются в сессии, а инженер
видит ошибку в логе.

**Ограничитель под лимиты Telegram.** Одно сообщение в секунду на чат, не
больше тридцати в секунду суммарно. Часы инжектятся, поэтому тест проверяет
расчёт паузы мгновенно.

**Ответы разбираются по-человечески.** Бюджет понимается как «5 млн»,
«5 000 000», «5,5 млн», «800к», «от 4 до 6 млн». Телефон нормализуется к
`+7XXXXXXXXXX` из любого формата. Вариант ответа принимается текстом, номером
или частью слова, но неоднозначное сокращение отклоняется, а не угадывается.

## Скоринг

Баллы складываются из срока, способа оплаты и бюджета. Пороги вынесены
в константы `scoring.py`.

| Фактор | Баллы |
|---|---|
| Покупка в течение месяца | 50 |
| Покупка 1-3 месяца | 35 |
| Ипотека одобрена | 30 |
| Свои средства | 25 |
| Бюджет от 15 млн | 30 |
| Бюджет от 8 млн | 20 |

От 75 баллов лид горячий, от 40 тёплый, ниже холодный. В комментарий к сделке
уезжает не только цифра, но и список причин: менеджер сразу видит, за что
начислены баллы.

## Запуск

```bash
pip install -e ".[dev]"
pytest
```

Прогон сценария на моках, без токена и без CRM:

```python
import asyncio
from leadbot import LeadBot, MockCRM, MockTransport, SessionStore

async def main():
    crm, transport = MockCRM(), MockTransport()
    bot = LeadBot(transport, crm, store=SessionStore("state/sessions.json"))

    for message in ("/start", "Квартира", "9 млн", "1-3 месяца",
                    "Ипотека одобрена", "89991234567"):
        await bot.handle(chat_id=1, text=message)

    for sent in transport.messages:
        print(">", sent.text)
    print(crm.created[0].comment())

asyncio.run(main())
```

Боевое подключение отличается только заменой адаптеров:

```python
from leadbot import Bitrix24CRM, LeadBot, RetryingCRM, SessionStore, TelegramTransport

crm = RetryingCRM(Bitrix24CRM("https://company.bitrix24.ru/rest/1/ТОКЕН"))
bot = LeadBot(
    TelegramTransport("ТОКЕН_БОТА"),
    crm,
    store=SessionStore("state/sessions.json"),
)
```

Дальше остаётся прокинуть входящие апдейты в `bot.handle(chat_id, text)`
из polling или вебхука.

## Тесты

51 тест. Помимо счастливого пути проверяются места, где такие боты обычно
и ломаются:

- разбор бюджета в десяти написаниях и отказ на мусоре
- неоднозначное сокращение варианта не угадывается, а переспрашивается
- невалидный ответ не двигает шаг анкеты
- повторная отправка не создаёт вторую сделку
- отказ по валидации не повторяется, недоступность повторяется
- падение CRM не теряет ответы и не показывает пользователю стектрейс
- незаконченная анкета переживает перезапуск процесса
- битый файл состояния не мешает старту
- запись состояния атомарна при падении посреди сохранения
- два чата не смешивают ответы
- ограничитель частоты выдерживает и поштучный, и общий лимит

## Структура

```
leadbot/
  dialogue.py   сценарий данными, разбор бюджета и телефона, состояние анкеты
  scoring.py    таблицы баллов, температура лида, причины начисления
  crm.py        протокол CRM, адаптер Битрикс24, мок, ретраи и дедупликация
  transport.py  протокол отправки, адаптер Telegram, мок, ограничитель частоты
  storage.py    сессии с атомарным снимком на диск
  app.py        связывание: сообщение -> анкета -> скоринг -> CRM
```
